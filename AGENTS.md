# PincerX — Agent Notes

## Stack
- Express.js server (`api/server.js`) serving static `public/index.html` (~5000 lines, inline JS).
- AI via `lib/ai.js` (Ollama / OpenAI-compatible). Default base URL: `http://host.docker.internal:11434` (Docker-host-aware).
- Zonos TTS for multi-voice audio.

## Key conventions
- Frontend is a single `index.html` with two inline `<script>` blocks. Validate syntax with:
  ```bash
  node -e "const fs=require('fs');const h=fs.readFileSync('public/index.html','utf8');[...h.matchAll(/<script(?![^>]*src=)[^>]*>([\s\S]*?)<\/script>/g)].forEach((s,i)=>{try{new Function(s[1]);console.log('ok',i)}catch(e){console.log('ERR',i,e.message)}})"
  ```
- `apiFetch(url, opts)` wraps `fetch` + `res.json()` and throws on `!res.ok` (error message from `data.error`).
- Global AI status bar (`#ai-status-bar`) surfaces generation phase + errors via `showAIStatus(text, type, detail, autoHideMs)`. `preflightAIConnection()` probes `/models` before long generation so unreachable backends fail fast instead of stalling on "Loading…".
- Live AI Conversation preview (`#ai-convo`, collapsible bottom-right panel) shows streaming generation in real time. Backed by SSE streaming endpoints: `POST /story/create/stream` and `POST /story/:id/chapter/stream`. These emit `progress`/`token`/`done`/`error` SSE events. Frontend `streamAIRequest(url, body, handlers)` parses the SSE stream via `fetch` + `ReadableStream.getReader()` (not `EventSource`, which only supports GET). `lib/ai.js#askStream(prompt, options, onToken)` streams from the AI backend (Ollama NDJSON / OpenAI SSE) with a buffered-JSON fallback. `story.js` accepts `onToken`/`onPhase` in `aiOptions` and routes to `askStream` when `onToken` is present.
- Coherence-guided regeneration: when a coherence check finds warnings, the Coherence tab shows a regeneration section (`#coherence-regen`) with the recommendation, an optional "Custom instructions" textarea, and a "🔄 Regenerate Chapter" button. Clicking it calls `regenerateChapterFromCoherence()` which hits the chapter stream endpoint with a `regenerate: { evidence, recommendation, customInstruction }` body. `story.js#generateChapter` detects `aiOptions.regenerate` and builds a regeneration prompt (preserving events/continuity, addressing the evidence, following the recommendation, and applying the custom instruction as an *additional* constraint — never a replacement for the coherence fix). Only the affected chapter is replaced; the original is preserved on failure (disk write happens only after successful generation). Coherence is auto-re-checked on the regenerated chapter and the panel refreshes; controls stay available for further iteration.
- Outline custom prompt: `story.js#create(title, genre, tone, aiOptions, customPrompt)` appends an "Additional instructions" block to the outline prompt when `customPrompt` is non-empty (mirrors the chapter `customPrompt` pattern). The Story Details section has a `#story-custom-prompt` textarea under the Model dropdown; `generateStory()` forwards it as `body.customPrompt` (only when non-empty). Both `POST /story/create` and `POST /story/create/stream` accept and trim `customPrompt`.

## Running
- `npm test` — 429 tests (jest). `npm start` / `node api/server.js` on port 3000.

## Reader Experience (emotional trajectory) subsystem
- Author-intent config (`story/story-experience.js#validateConfig`/`DEFAULT_CONFIG`). Values are stable machine-readable ids; display labels are a separate map (`EXPERIENCE_LABELS`) used only for UI `<option>` text and error messages. The vocabulary is the author's desired EXPERIENCE, not a list of writing rules:
  - Primary/Secondary ∈ `EXPERIENCE_CATEGORIES` = {curiosity, suspense, tension, mystery, emotional_investment, wonder, humor, excitement, romance, triumph}
  - Intensity ∈ `INTENSITY_LEVELS` = {low, moderate, high}
  - Pacing ∈ `PACING_LEVELS` = {slow, moderate, fast}
  - `DEFAULT_CONFIG` = {primary:curiosity, secondary:suspense, intensity:moderate, pacing:moderate}. `validateConfig` accepts either machine ids OR display labels at the boundary and always normalises to machine ids (single source of validation — do not duplicate). Returns `{valid, errors, normalized}`.
- UI (`public/index.html`): `REX_CATEGORIES`/`REX_INTENSITY`/`REX_PACING`/`REX_LABELS`/`REX_DEFAULTS` mirror the backend vocabularies. Dropdowns (`#rex-primary`/`#rex-secondary`/`#rex-intensity`/`#rex-pacing`) are populated deterministically by `_populateReaderExperienceOptions()` at page load (no LLM needed); `<option value="<machine-id>"><label>`. These constants MUST be declared in the SAME `<script>` block as the page-load init call that uses them, and BEFORE that call — otherwise a `const`/`let` temporal-dead-zone reference silently leaves all selects blank (the original bug). `_applyReaderExperienceSelection(REX_DEFAULTS)` selects the defaults when no story/config is loaded. `saveReaderExperienceConfig` POSTs the `.value` (machine ids) of each select. `tests/reader-experience-ui.test.js` source-extracts the HTML to prove options/defaults/TDZ-ordering without a browser.
- Stored as a per-story `reader_experience` RAG doc via `storyRag.setExperienceConfig`/`getExperienceConfig`/`getExperienceState`/`saveExperienceState` (added to `VALID_TYPES` — do NOT create a second storage system).
- Pipeline (`story.js#generateChapter`): before generation, `experience.synthesizeObjective(id, chapterNumber, aiOptions)` produces a structured chapter objective (currentState/targetState/readerQuestions/knowledgeManagement reveal-withhold-foreshadow/emotionalTrajectory/readerShouldDiscover/readerShouldNotDiscover/characterObjective/endingState/nextChapterPull). The synthesis prompt injects the config as "Author intent (Reader Experience config)" with BOTH the display label and machine id for each dimension, plus semantic guidance (primary=dominant, secondary=supporting NOT in every scene, intensity=driver strength NOT "make everything extreme", pacing=rate of experience change NOT sentence length) and an explicit instruction NOT to reduce it to a shallow "make it curious and suspenseful" / NOT to apply a fixed recipe. The LLM derives concrete, story-specific objectives from current state, prior chapters, reader-vs-character knowledge, unresolved questions, and trajectory. `experience.buildChapterObjectiveBlock(objective)` injects a compact block into the chapter prompt (does NOT dump the whole internal state). After generation + coherence, `experience.analyzeChapter(...)` soft-runs and returns findings (`{passed, observed, issues, recommendation}`); result includes `experience` + `experienceObjective`. State evolves in RAG (`trajectory`, `readerQuestions`, `currentState`).
- Chapter 1 is special: acquisition framing (immediate engagement, story promise, Chapter 2 anticipation, "Why should a new listener continue listening?"). Later chapters optimise for retention. No fixed hook formula — the synthesis LLM decides.
- Regeneration (`aiOptions.regenerate.experience = { findings, objective }`): folds experience feedback + objective into the regen prompt as additional constraints (never replacing coherence). The regen path reuses the provided objective (no new synthesis call) and re-analyses the regenerated chapter.
- Model propagation: `aiOptions.model` is forwarded to synthesis + analysis calls (maxTokens/streaming hooks stripped). Never hardcodes/falls back to another model.
- Repetition detection (`experience.detectRepetition`) scans chapter summaries via `storyRag.listDocs(id,'summary')`; flags `protagonist_wins` etc. and feeds the evidence into the synthesis prompt.
- Soft-fail: synthesis/analysis failures never block the chapter from saving; previous Reader Experience state is preserved. An unreachable LLM is reported via `error` on the result (do NOT mock Ollama to reproduce it).
- API endpoints (`api/server.js`): `GET/POST /story/:id/experience/config`, `GET /story/:id/experience/state`, `POST /story/:id/experience/synthesize`, `POST /story/:id/experience/analyze`. The chapter + chapter/stream endpoints accept `regenerate.experience`.
- UI: 🎯 Reader Experience config section (4 dropdowns, collapsible) in Story Details + an Experience sub-tab showing findings (✓/⚠), recommendation, and the synthesised objective preview. `regenerateChapterFromCoherence` forwards stored findings/objective; after regen it re-analyses experience.
- Tests: `tests/story-experience.test.js`, `tests/story-experience-integration.test.js`, +reader_experience tests in `tests/story-rag.test.js`, +experience endpoint tests in `tests/server.test.js`. Mock `ai.ask`/`story-rag`; no live LLM required.

## Name & Place Localization (canonical identity) subsystem
- Author-intent config (`story/story-localization.js#validateConfig`/`DEFAULT_CONFIG`). Values are stable machine ids; display labels are a separate map (`STYLE_LABELS`) used only for UI `<option>` text + error messages:
  - Style ∈ `LOCALIZATION_STYLES` = {original, english, english_distinctive, custom}. `DEFAULT_CONFIG` = {style:'original'}. `validateConfig` accepts either machine ids OR display labels at the boundary and always normalises to machine ids (returns `{valid, errors, normalized}`). `original` preserves existing behaviour — stories that pre-date the feature are UNAFFECTED.
  - `COMMON_NAMES` is a SMALL configurable list of overused English names to AVOID for `english_distinctive` (NOT a giant blacklist — the localization model is instructed to pick less-common but natural names; the list is just a hint).
  - `ENTITY_TYPES` = {character, place, city, country, company, organization, school, university, hospital, clan, sect, military, kingdom, district, business}.
- Stored as a per-story `entity_map` RAG doc (id `entity-map`) via `storyRag.saveEntityMapDoc`/`getEntityMapDoc`/`getLocalizationConfig`/`setLocalizationConfig`/`getEntityMap`/`ENTITY_MAP_DOC_ID` (added to `VALID_TYPES` — do NOT create a second storage system). The doc holds BOTH the config (`style`) AND the `entities[]` array — `setLocalizationConfig` preserves existing entities; `saveEntityMapDoc({entities})` preserves the stored config.
- Mapping shape: `{ id:'ent-<slug>', entityType, sourceNames:[...], canonicalName, displayName, userApproved, locked }`. ONE ENTITY = ONE CANONICAL IDENTITY. `addOrUpdateMapping(storyId, {entityType, sourceName, canonicalName, userApproved?, locked?})` is the single mutation entry point: prevents DUPLICATE canonical names across different entities (throws → API 409); respects `locked` mappings (a non-`userApproved` update cannot change a locked canonical name; a `userApproved:true` update can). `removeMapping(storyId, entityId)`.
- Alias resolution is the COHERENCE CONTRACT: `resolveNameWithMap(mapDoc, name)` / `resolveName(storyId, name)` return the canonical `displayName` if the name is a known source alias OR already canonical, else the original name unchanged. Coherence builds a `characterMap` keyed by BOTH source name AND canonical name pointing to the SAME character, so "Wei Chen" and "Cedric Vale" are NEVER reported as two different characters.
- `buildCanonicalNamesBlock(storyId)` returns '' when inactive OR no mappings (so prompts are unchanged for stories that don't use the feature); otherwise a compact `CANONICAL NAMES` block listing `sourceName → canonicalName` + "Use \"X\" in all generated prose." + "Do NOT revert to the source name or invent a new name." It does NOT leak internal ids/locked flags to the model.
- Pipeline (`story.js`): `create(title, genre, tone, aiOptions, customPrompt, localizationStyle='')` — when a localizing style is passed, the initial entities (from the outline LLM response) are localized once via `localizeEntities` (a single batched LLM call — the model is NEVER asked to rename the same character every chapter). `generateChapter` injects `canonicalNamesBlock` into the prompt (normal / resume / regeneration paths all include it). After generation + knowledge extraction, newly discovered entity names are localized via `localizeEntities` (skips already-mapped names). `localizeStory(storyId, aiOptions)` is the explicit "Localize Story Names" operation for EXISTING stories — scans existing RAG knowledge (characters/places/lore/system), proposes canonical names for unmapped entities, does NOT rewrite historical chapters (only future generation context is updated).
- Speaker-tag regexes (`story.js#_extractSpeakerNames` + `story-coherence.js#extractSpeakers`) were updated to allow SPACES (`[A-Za-z0-9 _-]+`) so multi-word canonical names like "Cedric Vale" in `[speaker:Cedric Vale]` tags are captured correctly rather than truncated to "Cedric". This was a pre-existing limitation that localization makes relevant.
- Model propagation: `aiOptions.model` is forwarded to `localizeEntities`/`localizeStory` (via `_cleanAiOptions` — strips streaming/transport hooks, keeps model/provider/apiKey/baseUrl/timeoutMs). Never hardcodes a model.
- Soft-fail: localization NEVER blocks chapter generation. LLM failures return `{localized:false, error}` and the existing entity map is preserved. An unreachable LLM is reported via `error` (do NOT mock Ollama to reproduce it).
- API endpoints (`api/server.js`): `GET/POST /story/:id/localization/config`, `GET /story/:id/localization/map`, `POST /story/:id/localization/map` (author override → 201/400/409), `DELETE /story/:id/localization/map/:entityId`, `POST /story/:id/localize`. Both `/story/create` and `/story/create/stream` accept + forward `localizationStyle` (6th arg to `story.create`).
- UI (`public/index.html`): `NLO_STYLES`/`NLO_LABELS`/`NLO_DEFAULTS` mirror the backend vocabularies. The `#nlo-style` dropdown is populated deterministically by `_populateLocalizationOptions()` at page load (no LLM needed); `<option value="<machine-id>"><label>`. These constants are declared in the SAME `<script>` block as the page-load init call and BEFORE it (TDZ-safe — the same class of bug that once left the Reader Experience selects blank). `_applyLocalizationSelection(style)` selects the current/​default style. `saveLocalizationConfig` POSTs the style. `loadLocalizationState` (wired into `loadStory` + called after `generateStory`) loads config + entities and renders the mapping panel (`_renderLocalizationEntityPanel`); each mapping is editable + lockable. `resetLocalizationUI` (wired into `resetStory`) resets to defaults. `generateStory` forwards `#nlo-style`.value as `body.localizationStyle` (only when non-default). A "🔄 Localize Story Names" button calls `POST /localize` for existing stories.
- Tests: `tests/story-localization.test.js` (46 — config, mapping CRUD, dup prevention, locked/approved, alias resolution, prompt block, parse, localizeStory/localizeEntities, backward compat), `tests/story-localization-integration.test.js` (7 — generation prompt includes canonical names, regeneration preserves them, coherence recognises aliases, existing stories unaffected, acceptance test), `tests/localization-ui.test.js` (10 — option table, defaults, TDZ ordering, load/reset/generate wiring), +entity_map tests in `tests/story-rag.test.js` (7), +localization endpoint tests in `tests/server.test.js` (18). Mock `ai.ask`/`story-rag`; no live LLM required. Full suite: 546 tests pass.


## AI Timeout / Resume subsystem
- Long-running chapter generation can time out (the model stalls, or `lib/ai.js#askStream` hits its `timeoutMs`). The timeout MUST NOT discard partial content. `askStream` classifies the error (`classifyStreamError`) and, when `isMeaningfulPartial(accumulated, MIN_PARTIAL_CHARS=40)` is true, attaches `.partial` (the streamed text so far) and `.reason` (`timeout`/`connection`/`transport`) to the rejected `Error` before destroying the request. Exports: `{ ask, askStream, listModels, normalizeBaseUrl, isMeaningfulPartial, classifyStreamError, MIN_PARTIAL_CHARS }`.
- `story.js#generateChapter` catches that error in the streaming path: if a meaningful partial exists, it persists the chapter with `status:'partial'`, `resumeAvailable:true`, `generation:{reason, length, wordTarget, dialogRatio, model, experienceObjective}` (captured so a resume reproduces the exact original conditions), and returns `{status:'partial', reason, resumeAvailable:true, content, chapterNumber, experienceObjective}` — WITHOUT running summary/knowledge-extraction/coherence/experience-analysis (those run only on a completed chapter). A timeout with NO meaningful partial (or a non-streaming `ai.ask` timeout) throws `Generation timed out before usable chapter content was received.` (a normal failure, no resume).
- Resume path: `generateChapter(storyId, chapterNumber, aiOptions, customPrompt)` detects `aiOptions.resume` (truthy), loads the existing partial chapter from disk, and calls `_buildResumePrompt({chapterNumber, existingPartial, remainingWords, remainingLengthPolicy, ...})` — a CONTINUATION prompt that includes the existing partial text and instructs the model to "continue writing from the EXACT end … CONTINUATION text only … do NOT repeat". `resumeTokenBudget(length, wordTarget, partialWordCount)` returns the REMAINING budget (`maxWords - partialWords`, floored at 1; `maxTokens` scaled accordingly, floored at 256) so cumulative length stays bounded across multiple resumes. The model is taken from the partial's `generation.model` (NOT silently switched). Overlap dedup: `stripContinuationOverlap(existing, continuation)` removes a duplicated leading passage if the model restated the existing tail. On success the chapter is marked `status:'complete'` and full post-processing runs. Exports include `{ wordCount, resumeTokenBudget, stripContinuationOverlap }`.
- Reader Experience on resume: the objective captured on the partial (`generation.experienceObjective`) is REUSED — `experience.synthesizeObjective` is NOT called again — so the continuation targets the SAME emotional trajectory. `result.experienceObjective.reused === true` distinguishes this from a fresh synthesis.
- Multiple sequential resumes are supported: each resume reads the (possibly grown) partial from disk and recomputes the remaining budget, so a resume that times out again just leaves a larger partial for the next attempt.
- Backward compat: legacy chapters without a `status` field are treated as `complete` (default). `loadStory`/`storyState.nextChapter` skip partials when computing the next chapter number (a partial does not advance the counter — resume continues the same chapter).
- API (`api/server.js`): both `POST /story/:id/chapter` and `POST /story/:id/chapter/stream` accept a `resume` object in the body (forwarded into `aiOptions.resume`). A `status:'partial'` result returns HTTP 202 (non-stream) or an `event: partial` SSE event (stream) — NOT `done` — so the client shows the resume UI instead of treating it as a completed chapter. The stream endpoint SSE events are now `progress`/`token`/`partial`/`done`/`error`.
- UI (`public/index.html`): `streamAIRequest` handles the `partial` SSE event via an `onPartial(partial)` handler. `showPartialChapterBanner(chapterNumber, partial)` renders a banner with three actions: **▶ Resume Chapter** (`resumeChapterUI` — POSTs `{chapterNumber, resume:{}}`, reuses the same model, handles a second timeout by refreshing the banner), **↻ Regenerate Chapter** (`regenerateChapterFromScratch` — deletes the partial then generates fresh), **🗑 Discard** (`discardPartialChapterUI` — DELETEs the partial chapter). `loadStory` detects a persisted partial and shows the banner on page reload (resume works across sessions). `generateNextChapter` (both the base and the Story Writer override) resolve `{__partial:true, ...partial}` and skip the completed-chapter post-processing. CSS: `.partial-banner` (blue) near the chapter message area.
- Tests: `tests/chapter-resume.test.js` (23 tests — resume helpers, ai partial classification, timeout-with-partial preservation, timeout-before-output, resume continuation/dedup/budget/model/objective, multiple sequential resumes, backward compat, Reader Experience reuse), +partial/resume endpoint tests in `tests/server.test.js`, +partial-on-timeout tests in `tests/ai.test.js`. Mock `ai.askStream`/`ai.ask`/`story-rag`/`story-coherence`; no live LLM required (the `lib/ai` mock factory uses `jest.requireActual` to keep the real `isMeaningfulPartial`/`classifyStreamError`).

## Browser-tool caveat
The browser automation tool can get stuck on `about:blank` (no tabs) mid-session and aggressively caches inline JS. When it fails, verify via `curl` against the server + server logs instead of fighting the browser.
